# Requirements — 蛙游记 Froggy Trails (v1)

## Intent Analysis

- **User Request**: 做一个"旅行小动物"的 Web App,用户可以自己选角色;基于已有的初步 PRD(蛙游记 Froggy Trails)。
- **Request Type**: New Project (greenfield)
- **Scope Estimate**: System-wide — 完整 Web 应用(小屋/行囊/地图/相册/商店 + 异步旅行引擎 + 内容系统 + 本地存档)
- **Complexity Estimate**: Complex(异步状态机、内容组合系统、本地持久化、双语、响应式)
- **Requirements Depth**: Comprehensive
- **Reference**: `froggy-trails-prd_2828/froggy-trails-prd.md`(Concept/MVP Definition, v0.1)

## v1 Scope Decisions (来自澄清问答)

| # | 决策 | 选择 |
|---|---|---|
| Q1 | 角色 | 新手从少数小动物(蛙/獭/刺猬)中选一只,选定后固定;单角色养成 |
| Q2 | 旅行结算 | 客户端**惰性结算**:出发时存 departure/arrival/return 时间 + `random_seed`,打开时按时间推进补算 |
| Q3 | 内容生成 | **预制素材库**:固定明信片图 + 固定日记文案,运行时按 地点×天气×姿势 组合展示 |
| Q4 | 真实世界数据 | **内置种子数据**(经纬度/简介/气候),地图静态点亮,首版**不接外部 API** |
| Q5 | 存档 | **纯游客本地存档**(IndexedDB),无账号、无云同步 |
| Q6 | 技术栈 | 前端 PRD 建议栈;首版**无后端/数据库**,数据模型按 PRD §21 设计但落在本地存储层 |
| Q7 | 平台 | **桌面 Web 优先** + 响应式移动适配;PWA/推送留 P1 |
| Q8 | 商店 | 仅**软货币(三叶草)**,**不接真实支付** |
| Q9 | 语言 | **中英双语**(i18n) |
| Q10 | 目标 | 一个跑通完整核心闭环的**可玩 Demo**,内容少而精 |

**内容规模(v1)**:PRD MVP 建议 30 个地点;依据 Q10"少而精",v1 先做 **8–12 个地点**,数据结构与内容 pipeline 按可扩展到 30 设计。

**核心闭环(v1 必须跑通)**:选角色/命名 → 领新手道具 → 准备行囊 → 出发 → 等待(惰性推进)→ 收到明信片/事件 → 归来 → 获得纪念品/地点知识 → 地图点亮 / 相册成长 → 再次出发。

## Functional Requirements

### FR-1 新手引导与角色选择
- FR-1.1 首次进入展示新手引导;用户从固定的少数小动物(蛙、獭、刺猬,数量以素材库为准)中**选择一只**作为长期伙伴,选定后不可更换。
- FR-1.2 用户为角色**命名**。
- FR-1.3 发放新手道具:一块面包(食物)、一个水壶(装备)、20 三叶草(软货币)。
- FR-1.4 引导用户完成第一次"准备行囊 → 出发",**首趟时长压缩到 3–8 分钟**,确保首次会话内看到完整闭环。

### FR-2 小屋 / 首页(核心页面)
- FR-2.1 展示庭院、小屋、角色、邮箱等场景;桌面端左侧场景(~65%)+ 右侧状态栏(~35%),移动端为响应式堆叠布局。
- FR-2.2 右侧状态栏显示:角色名、心情、当前状态、当前资源(三叶草等)、"准备行囊"入口、最近一张明信片、未读邮件、季节/天气氛围。
- FR-2.3 **庭院资源采集**:周期性生成 普通三叶草(基础软货币)/ 四叶草(低概率幸运道具)/ 露珠(装饰资源)。规则:不上线不产生损失、无"过期"、一次操作即可收取、无高频收菜压力。
- FR-2.4 首页环境动效(树叶摇动、云移动、角色眨眼、来信时邮箱轻晃)——氛围性,不阻塞交互。

### FR-3 角色状态机
- FR-3.1 状态机:`HOME_IDLE → PACK_READY → DEPARTING → TRAVELING → RETURNING → HOME_IDLE`。
- FR-3.2 旅行途中**不展示实时 GPS/精确位置**;仅展示氛围型文字状态(例:"正在向很远的地方走去""今天似乎遇到了雨"),保留未知感。

### FR-4 行囊系统
- FR-4.1 四类行李槽位:食物、护符、装备A、装备B;用户从库存拖入/放入槽位。
- FR-4.2 每类槽位对旅行结果有影响:食物(时长/区域偏好)、护符(稀有事件概率)、装备A(地形/气候)、装备B(明信片/纪念品倾向)。
- FR-4.3 **模糊提示**:界面只给氛围化倾向提示(例:"似乎适合寒冷地区""也许会走得更远"),**不直接显示目标地点**。
- FR-4.4 "确认行囊"后进入 `PACK_READY`,可发起出发。

### FR-5 旅行生成系统(客户端惰性结算)
- FR-5.1 出发时记录:出发时间、预计到达/归来时间、所选行囊、`random_seed`、状态。
- FR-5.2 目的地选择基于加权评分:`DestinationScore = BaseWeight × EquipmentMatch × FoodMatch × SeasonMatch × NoveltyBoost × RarityFactor × RandomFactor`(具体因子取值与是否硬门槛在功能设计阶段定义)。
- FR-5.3 **NoveltyBoost**:连续访问同一国家/区域时,未访问区域获得轻度概率提升,但不完全阻止重复;重复旅行仍产出内容(地点×季节×天气×稀有事件产生差异)。
- FR-5.4 旅行时长分层:新手首趟 3–8 分钟;普通 30 分钟–8 小时;远行 8–24 小时;稀有远行 1–3 天(v1 可用压缩配置便于体验/测试)。
- FR-5.5 **惰性推进**:用户打开应用时,依据当前时间与出发时记录的时间线+种子,确定性地推进状态与结算旅行产物(同一 seed 可复现)。
- FR-5.6 一次旅行至少产出以下三类中的**两类**:故事、地点、收藏。

### FR-6 明信片系统
- FR-6.1 旅行期间产出 0–2 张明信片;归来时补充 0–1 张。
- FR-6.2 明信片数据含:地点、场景、角色姿势、同行者、天气、稀有度、日记文案、生成时间、图片引用。
- FR-6.3 图片来自**预制素材库**,按 地点×天气×姿势 组合;日记文案取自该地点的固定文案池。
- FR-6.4 稀有度用**纸张/边框/邮戳/星空纸/手绘签名/限定季节纸**等表现,**不使用抽卡/SSR 语言**。
- FR-6.5 收到明信片以"卡片滑入桌面"的方式呈现,**不使用普通 Toast**。

### FR-7 旅行相册(手帐 / Scrapbook)
- FR-7.1 采用手帐/剪贴簿式跨页布局(左页大图明信片,右页日期/地点/天气/邮戳/日记/纪念品/地点知识),非普通网格。
- FR-7.2 **分享卡生成**:输出含 画面 + 地名 + 日期 + 一句话 + 品牌角标 的图片,可下载/保存。

### FR-8 世界地图(回顾工具)
- FR-8.1 地图为"它去过哪里"的回顾工具,**非行程规划工具**。
- FR-8.2 层级:世界 → 国家 → 城市/景点。
- FR-8.3 地点状态:未发现 / 听说过 / 去过 / 多次到访 / 完成收藏;初始覆盖轻度迷雾,访问后逐渐点亮。
- FR-8.4 v1 使用内置种子地点数据,静态点亮效果(不接实时 tile/外部 API)。

### FR-9 纪念品系统
- FR-9.1 每个地点配置 3–8 个纪念品(可含"无意义但有情绪"的物件)。
- FR-9.2 旅行归来按规则发放纪念品;纪念品计入收藏并在相册/地图中体现。

### FR-10 商店
- FR-10.1 商店仅使用**软货币(三叶草)**购买 食物 / 装备 / 装饰;**不接入任何真实支付**。
- FR-10.2 购买后进入库存,可用于行囊或装饰小屋。

### FR-11 存档与数据(本地)
- FR-11.1 全部用户数据(角色、库存、旅行、明信片、纪念品、地点访问、成就等)存储在浏览器 **IndexedDB**;无账号、无云同步。
- FR-11.2 数据模型按 PRD §21 设计(users/frogs/items/user_inventory/destinations/trips/postcards/souvenirs/user_souvenirs/destination_visits/visitors/notifications/achievements),v1 以本地存储集合形式实现。
- FR-11.3 `trips` 保存 `random_seed` 以支持旅行复现与调试。
- FR-11.4 清除浏览器数据会丢失存档(v1 已知限制);后续 P1 增加云同步。

### FR-12 通知(应用内)
- FR-12.1 v1 提供**应用内**事件反馈(角色回家、收到明信片);带故事感文案。
- FR-12.2 PWA 安装与系统级推送为 P1(v1 不实现)。

### FR-13 国际化(i18n)
- FR-13.1 界面文案支持**中文与英文**双语,可切换;内容文案(日记/地点介绍)首版至少提供中文,英文可分批补齐(具体在功能设计确定)。

### FR-14 埋点(轻量)
- FR-14.1 记录核心闭环事件(onboarding、clover_harvested、backpack_confirmed、trip_started、postcard_received/opened、trip_completed、souvenir_received、destination_unlocked、postcard_shared 等)。
- FR-14.2 v1 无外部分析服务,埋点先落本地/可插拔接口,便于 P1 接入 PostHog。

## Non-Functional Requirements

### NFR-1 平台与兼容
- 桌面 Web 优先,响应式适配移动端浏览器;支持主流现代浏览器最新两个版本。

### NFR-2 性能
- 首页首次可交互 < 3s(常规宽带);动效不阻塞主线程;明信片/素材图按需加载。

### NFR-3 离线 / 本地优先
- 核心玩法在本地运行,不依赖网络(除首次加载静态资源);惰性结算在客户端完成。

### NFR-4 可维护 / 可扩展
- 地点、明信片、纪念品、日记等**内容与代码分离**,以数据/素材清单驱动,可从 ~10 个地点平滑扩展到 30+ 而无需改核心逻辑。
- 旅行算法各因子参数可配置。

### NFR-5 可访问性
- 遵循基本 WCAG 实践:语义化结构、键盘可达、足够对比度、图片替代文本、尊重"减少动效"偏好(prefers-reduced-motion)。

### NFR-6 视觉一致性
- 严格遵循 PRD §25 视觉方向(森林手帐/watercolor/暖纸张、指定配色、圆角卡片、弱阴影、手绘图标,避免 SaaS 风与大量数值/进度条)。

### NFR-7 数据完整性 / 确定性
- 相同 `random_seed` + 相同行囊 + 相同时间线必须复现相同旅行结果。
- 本地存档写入应具备基本容错(避免半写导致存档损坏)。

### NFR-8 版权 / IP 合规
- 遵循 PRD §29:不使用《旅行青蛙》名称/角色造型/房间布局/UI/明信片构图;角色、美术、UI、世界观全部原创。
- v1 素材(明信片/角色/纪念品插画)须为原创或具备合规授权。

### NFR-9 内容安全
- 预制文案与素材需人工审核,避免不当内容(v1 无运行时 AI 生成,风险较低)。

## Out of Scope (v1)

- 后端服务、数据库、账号系统、云同步(P1)
- 实时地图 tile / 天气 API / 维基数据接入(P1+)
- 运行时 AI 生成明信片/日记(P2)
- PWA 系统级推送通知(P1)
- 真实支付 / 商业化(装饰付费、Season Pass)(P1)
- 朋友来访、成就系统全量、季节系统、社交/好友互访、UGC 明信片、多只小蛙同时养成(P1/P2)
- 30 个地点全量内容(v1 先 8–12 个)

## Key Requirements Summary

- **一句话**:纯前端(Next.js + React + TS + Tailwind + Framer Motion)、IndexedDB 本地存档的 cozy 异步旅行养成 Web App,跑通"选角色→准备→出发→惰性等待→收明信片→归来→点亮地图/相册"完整闭环,内容少而精(8–12 地点),中英双语,桌面优先响应式,商店仅软货币,严格原创视觉。
- **技术核心**:客户端惰性、可复现(seed)的旅行结算引擎 + 数据/素材驱动的内容组合系统。
- **首版已知取舍**:清缓存会丢档、无离线推送、无真实数据接入——均为有意的 v1 边界,P1 再补。
